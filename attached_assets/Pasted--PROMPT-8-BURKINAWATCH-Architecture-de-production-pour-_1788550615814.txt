# PROMPT 8 — BURKINAWATCH

## Architecture de production pour caméras distantes, NAT/CGNAT et Video Gateway

Tu travailles sur le projet BurkinaWatch existant.

Cette phase vient APRÈS le Prompt 7.

Le Prompt 8 ne doit pas ajouter de nouvelles fonctionnalités métier inutiles.

Son objectif est de préparer une architecture réellement capable de supporter des caméras IP appartenant à des utilisateurs situés sur différents réseaux, notamment derrière :

* NAT ;
* CGNAT ;
* box Internet ;
* réseaux mobiles ;
* réseaux professionnels ;
* réseaux privés ;
* connexions Internet instables.

IMPORTANT :

* Ne réécris pas BurkinaWatch.
* Ne casse aucune fonctionnalité existante.
* Ne remplace pas l'architecture existante sans justification.
* Ne transforme pas Express en serveur vidéo.
* Ne demande jamais d'exposer publiquement le port RTSP 554 d'une caméra.
* Ne demande jamais de mettre une caméra en DMZ.
* Ne désactive jamais le firewall d'un utilisateur.
* Ne contourne jamais NAT/CGNAT par une méthode dangereuse.
* Ne mets jamais de credentials caméra dans le frontend.
* Ne mets jamais de secrets dans Git.
* Ne déploie aucune nouvelle infrastructure coûteuse sans nécessité.
* Ne déploie rien en production sans validation.
* Ne lance aucune migration destructive.
* Ne lance jamais `db:push --force`.

# 3. ARCHITECTURE CIBLE

Préparer l'architecture suivante :

```text
                    BURKINAWATCH
                 CONTROL PLANE
                        │
              Auth / API / PostgreSQL
                        │
                        │
              ┌─────────▼─────────┐
              │   Video Gateway   │
              │     MediaMTX      │
              └─────────┬─────────┘
                        │
                     WebRTC
                        │
                        ▼
                    Utilisateur
                    navigateur
```

Pour une caméra directement accessible depuis le gateway :

```text
Caméra IP
    │
   RTSP
    │
    ▼
MediaMTX
    │
  WebRTC
    │
    ▼
BurkinaWatch
```

Pour une caméra derrière NAT/CGNAT :

```text
Caméra IP
    │
    ▼
Agent local / Gateway local
    │
    │ connexion SORTANTE sécurisée
    ▼
Infrastructure BurkinaWatch
    │
    ▼
MediaMTX
    │
   WebRTC
    │
    ▼
Utilisateur
```

L'objectif de cette phase est de préparer cette architecture.

# 4. PRINCIPE FONDAMENTAL

Le serveur BurkinaWatch ne doit PAS avoir besoin d'établir une connexion entrante vers chaque réseau domestique.

Privilégier lorsque nécessaire :

CONNEXION SORTANTE

plutôt que :

CONNEXION ENTRANTE.

Cela permet notamment de fonctionner avec :

* NAT ;
* CGNAT ;
* box 4G/5G ;
* certains réseaux professionnels.

---

# 5. AGENT LOCAL

Étudier l'introduction future d'un composant :

`BurkinaWatch Camera Agent`

Son rôle éventuel :

* fonctionner dans le réseau local du propriétaire ;
* accéder à la caméra ;
* récupérer le flux RTSP ;
* établir une connexion sortante sécurisée vers l'infrastructure BurkinaWatch ;
* publier le flux vers le Video Gateway ;
* transmettre uniquement le flux nécessaire.

IMPORTANT :

Ne pas développer immédiatement un agent complexe si l'audit montre qu'il n'est pas encore nécessaire.

Si sa nécessité est confirmée, préparer une architecture propre et un MVP minimal.

---

# 6. AGENT LOCAL : CE QU'IL NE DOIT PAS FAIRE

L'agent ne doit pas devenir :

* un scanner réseau ;
* un proxy Internet général ;
* un tunnel arbitraire ;
* un accès shell distant ;
* un outil de contrôle de machines ;
* un service permettant d'atteindre d'autres appareils du LAN.

Il doit avoir une fonction extrêmement limitée :

CAMÉRA → FLUX VIDÉO → BURKINAWATCH

---

# 7. IDENTITÉ DE L'AGENT

Chaque agent doit disposer d'une identité propre.

Exemple conceptuel :

agentId

L'identité doit être :

* unique ;
* aléatoire ;
* révocable ;
* associée à un utilisateur ;
* éventuellement associée à une ou plusieurs caméras.

Ne pas utiliser simplement :

cameraId

comme mécanisme d'authentification.

---

# 8. ENREGISTREMENT DE L'AGENT

Préparer un mécanisme sécurisé d'enrôlement.

Architecture conceptuelle :

Utilisateur connecté à BurkinaWatch

↓

"Ajouter un agent"

↓

BurkinaWatch génère une procédure d'enrôlement temporaire

↓

Agent local s'enregistre

↓

Serveur vérifie l'enrôlement

↓

Agent reçoit son identité/token

↓

Agent établit une connexion sortante sécurisée.

Les codes ou tokens d'enrôlement doivent être :

* temporaires ;
* à usage limité ;
* non prédictibles ;
* révocables.

Ne jamais utiliser un token permanent affiché dans l'interface.

---

# 9. AUTHENTIFICATION AGENT ↔ SERVEUR

L'agent doit s'authentifier auprès du backend.

Étudier l'option la plus appropriée entre :

* token rotatif ;
* clé API dédiée ;
* mTLS ;
* autre mécanisme adapté.

Ne choisis pas une technologie uniquement parce qu'elle est populaire.

Choisis selon :

* sécurité ;
* complexité ;
* déploiement ;
* maintenance ;
* rotation ;
* révocation ;
* compatibilité avec l'infrastructure BurkinaWatch.

Documenter le choix.

---

# 10. CONNEXION SORTANTE

Si un agent est nécessaire, privilégier :

Agent
→ connexion sortante TLS
→ BurkinaWatch

Le serveur ne doit pas avoir besoin de connaître :

* l'adresse publique du domicile ;
* le port RTSP public ;
* la configuration de la box.

L'agent peut alors récupérer localement :

rtsp://camera-local/...

et publier vers le système BurkinaWatch.

---

# 11. PAS DE RTSP PUBLIC

RÈGLE ABSOLUE :

Ne jamais demander à l'utilisateur de faire :

Internet
→ port 554
→ caméra.

Une caméra utilisateur ne doit pas devenir publiquement accessible simplement pour fonctionner avec BurkinaWatch.

Si une documentation existante demande cette configuration :

corrige-la.

---

# 12. MEDIA GATEWAY

Le Media Gateway doit rester séparé du backend métier.

BurkinaWatch backend :

* utilisateurs ;
* droits ;
* caméras ;
* agents ;
* tokens ;
* configuration.

MediaMTX :

* ingestion ;
* RTSP ;
* WebRTC ;
* transport vidéo.

Ne pas ajouter la vidéo dans les routes Express.

---

# 13. API MEDIA GATEWAY

Vérifier que l'API administrative de MediaMTX n'est pas exposée publiquement.

Si une API de contrôle existe :

elle doit être accessible uniquement depuis les composants autorisés.

Ne jamais exposer :

* API admin MediaMTX ;
* credentials gateway ;
* configuration interne ;
* endpoints de publication arbitraire.

---

# 14. TLS

Tout trafic de contrôle distant doit utiliser TLS.

Vérifier :

* HTTPS ;
* certificats ;
* validation TLS ;
* expiration ;
* renouvellement.

Ne jamais utiliser :

HTTP non chiffré

pour une communication agent ↔ serveur en production.

---

# 15. WEBSOCKET / QUIC / TCP / UDP

Si un agent distant est nécessaire, analyser objectivement le protocole de transport.

Comparer selon le besoin :

* HTTPS ;
* WebSocket ;
* TCP/TLS ;
* QUIC ;
* autres solutions appropriées.

Critères :

* NAT traversal ;
* fiabilité ;
* latence ;
* simplicité ;
* support infrastructure ;
* sécurité ;
* coût.

Ne pas ajouter QUIC ou une technologie complexe simplement pour "faire moderne".

Choisir la solution la plus simple qui répond réellement au problème.

# 24. RÉVOCATION D'UN AGENT

L'utilisateur doit pouvoir désactiver un agent.

→ serveur

doit être refusé.

# RÈGLE ABSOLUE

Le but de cette phase n'est PAS de faire fonctionner une caméra à n'importe quel prix.

Le but est de construire la fondation technique qui permettra à BurkinaWatch de passer progressivement de :

1 utilisateur
→ 1 caméra
→ 1 réseau
