# PROMPT 6 — BURKINAWATCH

## Intégration contrôlée d’une vraie caméra IP dans le système de vidéosurveillance

Tu travailles sur le projet BurkinaWatch existant.

IMPORTANT :

* Tu dois travailler à partir du code existant.
* Tu ne dois pas réécrire l’application.
* Tu ne dois pas remplacer l’architecture existante sans justification.
* Tu ne dois pas casser les fonctionnalités existantes.
* Tu ne dois pas modifier inutilement l’UI générale de BurkinaWatch.
* Tu dois préserver toutes les protections de sécurité déjà mises en place.
* Tu dois avancer progressivement.
* Tu ne dois jamais exposer de mot de passe caméra, URL RTSP, token vidéo ou secret au frontend.
* Tu ne dois jamais demander à l’utilisateur d’exposer publiquement le port RTSP 554 de sa caméra.
* Tu ne dois jamais désactiver une protection de sécurité pour faire fonctionner le prototype.

L’objectif de cette phase est de passer du prototype avec source vidéo de test à une véritable caméra IP physique, mais uniquement dans un environnement contrôlé de développement/préproduction.

---

# 1. OBJECTIF GLOBAL

Valider réellement la chaîne suivante :

Caméra IP réelle
↓
RTSP / éventuellement ONVIF
↓
Media Gateway / MediaMTX
↓
WebRTC
↓
BurkinaWatch
↓
Utilisateur authentifié et autorisé

Le système doit permettre à un utilisateur propriétaire d’une caméra enregistrée dans BurkinaWatch de demander son flux live et de le visualiser dans l’interface web.

Cette phase ne doit PAS encore implémenter :

* enregistrement vidéo ;
* stockage vidéo ;
* détection IA ;
* reconnaissance faciale ;
* partage public ;
* partage par lien ;
* réseau de caméras publiques ;
* scan automatique du réseau ;
* découverte automatique de toutes les caméras Internet ;
* accès administrateur arbitraire aux caméras des utilisateurs ;
* exposition publique du RTSP ;
* proxy vidéo à travers Express.

# 4. CONFIGURATION D’UNE VRAIE CAMÉRA IP

Le système doit permettre d'utiliser une caméra IP réelle de test.

La caméra peut être :

* sur le même réseau local que le gateway ;
* ou accessible depuis le gateway via un réseau privé/VPN approprié.

NE PAS exposer directement la caméra sur Internet uniquement pour rendre le test possible.

NE PAS demander :

"ouvre le port 554 sur ta box".

NE PAS demander :

"mets la caméra en DMZ".

NE PAS désactiver le firewall.

NE PAS utiliser une URL RTSP publique non sécurisée comme architecture de production.

---

# 5. INFORMATIONS CAMÉRA

Le backend doit pouvoir gérer les informations nécessaires à la connexion :

* adresse IP / hostname ;
* port RTSP ;
* chemin RTSP ;
* username ;
* password ;
* protocole ;
* modèle éventuel ;
* statut ;
* gateway/path associé.

Les credentials doivent rester exclusivement côté serveur.

Le frontend ne doit jamais recevoir :

* password ;
* username si inutile ;
* RTSP URL complète ;
* RTSP credentials ;
* secret gateway.

---

# 6. CHIFFREMENT DES CREDENTIALS

Utilise le système de chiffrement déjà présent dans BurkinaWatch.

Si le projet dispose déjà de :

AES-256-GCM

utilise-le.

Ne crée pas un deuxième système de chiffrement concurrent.

Les credentials caméra doivent être :

* chiffrés au repos ;
* déchiffrés uniquement côté serveur lorsqu'ils sont nécessaires ;
* jamais renvoyés dans une réponse API ;
* jamais écrits dans les logs ;
* jamais affichés dans le frontend ;
* jamais inclus dans une URL publique.

Si `MASTER_ENCRYPTION_KEY` est obligatoire en production, conserve cette exigence.

Ne crée aucun fallback dangereux avec une clé aléatoire à chaque démarrage.

---

# 7. TEST DE CONNECTIVITÉ CAMÉRA

Créer ou compléter une fonctionnalité backend permettant de vérifier qu'une caméra est réellement joignable.

Exemple conceptuel :

POST /api/surveillance/cameras/:id/test-connection

Le serveur doit :

1. authentifier l'utilisateur ;
2. récupérer la caméra ;
3. vérifier que l'utilisateur possède cette caméra ou dispose explicitement de la permission nécessaire ;
4. appliquer la validation SSRF ;
5. récupérer les credentials chiffrés ;
6. tenter la connexion RTSP ;
7. retourner uniquement un résultat abstrait.

Exemple :

{
"success": true,
"status": "online"
}

ou :

{
"success": false,
"status": "offline"
}

Ne retourne jamais :

* password ;
* RTSP URL ;
* détails internes inutiles ;
* stack trace ;
* secret ;
* credentials.

---

# 8. ATTENTION À LA SSRF

La validation SSRF existante doit être conservée.

Une caméra enregistrée ne doit pas permettre de transformer BurkinaWatch en scanner/proxy réseau.

Bloquer notamment :

* localhost ;
* 127.0.0.1 ;
* loopback IPv6 ;
* metadata endpoints ;
* adresses privées non explicitement autorisées ;
* link-local ;
* multicast ;
* schémas non autorisés ;
* URLs contenant username/password si le système ne les supporte pas explicitement.

IMPORTANT :

Le fait qu'une adresse soit fournie par un utilisateur ne signifie pas qu'elle doit être considérée comme sûre.

Si l'architecture nécessite exceptionnellement une adresse privée pour le test local, mettre en place une stratégie explicite d'environnement de développement plutôt que de supprimer globalement la protection SSRF.

---

# 9. ENREGISTREMENT DE LA CAMÉRA DANS MEDIAMTX

Si MediaMTX est le gateway retenu lors de la phase précédente, utilise son architecture existante.

Le backend doit pouvoir associer une caméra BurkinaWatch à un path MediaMTX.

Exemple conceptuel :

camera ID :
cam_123

gateway path :
camera_cam_123

Le nommage doit être déterministe et non devinable de manière dangereuse.

Ne mets jamais :

username/password

dans le frontend.

Évite également de stocker une RTSP URL complète avec credentials en clair.

---

# 10. ARCHITECTURE CONTROL PLANE / MEDIA PLANE

Cette séparation doit rester stricte.

## Control plane

BurkinaWatch :

* authentification ;
* utilisateurs ;
* caméra ;
* ownership ;
* permissions ;
* configuration ;
* statut ;
* création de tokens ;
* audit ;
* sécurité.

## Media plane

MediaMTX :

* RTSP ;
* conversion/transport ;
* WebRTC ;
* diffusion du flux.

Express ne doit PAS devenir un proxy vidéo.

Ne crée pas une route du type :

GET /camera/:id/video

qui streamerait toute la vidéo via Node.js.

---

# 11. DÉMARRAGE DU FLUX

Lorsqu'un utilisateur clique sur :

"Voir le direct"

le frontend doit appeler l'API BurkinaWatch.

Le backend :

1. authentifie l'utilisateur ;
2. vérifie ownership/permission ;
3. vérifie l'état de la caméra ;
4. prépare ou active le stream gateway ;
5. génère un accès vidéo temporaire ;
6. renvoie uniquement les informations nécessaires au lecteur WebRTC.

Le frontend ne doit jamais recevoir les secrets de connexion à la caméra.

---

# 12. TOKENS VIDÉO

Les tokens doivent être :

* courts ;
* temporaires ;
* aléatoires ;
* liés à l'utilisateur ;
* liés à la caméra ;
* idéalement liés à une session ;
* invalidables ;
* inutilisables après expiration.

Un token destiné à :

camera A

ne doit jamais fonctionner pour :

camera B.

Un utilisateur sans permission sur camera A ne doit jamais pouvoir créer lui-même un token valide.

Ne mets jamais de token permanent dans le code frontend.

Ne mets jamais de token secret dans une URL permanente.

---

# 13. WEBRTC

Le navigateur doit recevoir le flux via WebRTC.

Architecture :

Camera
→ RTSP
→ MediaMTX
→ WebRTC
→ Browser

Le navigateur ne doit jamais essayer de lire directement :

rtsp://...

Les composants WebRTC doivent gérer :

* connecting ;
* connected ;
* live ;
* disconnected ;
* reconnecting ;
* offline ;
* error.

Afficher un état clair à l'utilisateur.

---

# 20. CODECS

Tester notamment si nécessaire :

* H.265 ;

* Opus ;
* autres codecs pertinents.

# 21. NAT / RÉSEAUX DISTANTS

Tester le cas où :

Caméra ≠ même réseau que MediaMTX.

Identifier :

* NAT ;
* firewall ;
* CGNAT ;
* STUN ;
* TURN ;
* connectivité WebRTC.

Si TURN est nécessaire, documenter précisément :

* pourquoi ;

* quels ports sont nécessaires ;
* quelles mesures de sécurité sont nécessaires.

---

# 22. ONVIF

Si la caméra supporte ONVIF, vérifier si son utilisation apporte une vraie valeur.

ONVIF peut être utilisé pour :

* découverte contrôlée ;
* récupération des capacités ;
* récupération du profil média ;
* récupération de l'URL RTSP.

Mais :

NE PAS créer un scanner ONVIF global.

NE PAS scanner automatiquement tout le réseau.

NE PAS permettre à un utilisateur de demander au serveur de scanner arbitrairement des plages IP.

Si ONVIF n'est pas nécessaire au fonctionnement du MVP, le laisser hors périmètre.

---

# 30. CRITÈRES DE RÉUSSITE

La phase est considérée comme réussie uniquement si :

1. Une vraie caméra IP peut être enregistrée.
2. Ses credentials restent chiffrés.
3. Le backend peut vérifier sa connectivité.
4. MediaMTX peut récupérer son flux RTSP.
5. WebRTC peut transporter le flux.
6. Le navigateur peut afficher le direct.
7. Un utilisateur autorisé peut regarder.
8. Un utilisateur non autorisé ne peut pas regarder.
9. Un token expiré est refusé.
10. Les credentials n'apparaissent jamais côté frontend.
11. Aucun secret n'apparaît dans les logs.
12. L'architecture ne transforme pas Express en proxy vidéo.
13. La protection SSRF reste active.
14. Le système gère caméra offline/reconnexion.
15. Les tests automatisés passent.
16. Les fonctionnalités existantes de BurkinaWatch restent fonctionnelles.

# RÈGLE ABSOLUE

Ne passe pas à une architecture de production publique simplement parce que le flux fonctionne avec une caméra.

Cette phase sert à prouver que la chaîne technique fonctionne réellement avec une caméra IP.

Après cette phase, nous déciderons séparément de l'architecture de production :

* caméra locale ;
* caméra distante ;
* agent local ;
* VPN ;
* TURN ;
* scaling ;
* monitoring ;
* haute disponibilité ;
* enregistrement ;
* stockage ;
* IA.

Ne mélange pas ces sujets dans cette phase.

Commence par l'audit, puis implémente uniquement ce qui est nécessaire pour obtenir un live réel sécurisé.
