# BURKINAWATCH — PHASE 1.1

## VALIDATION ET MISE EN SERVICE DE LA PRODUCTION RAILWAY

### CONTEXTE

La Phase 1 d’audit/stabilisation vient d’être exécutée.

Le rapport a confirmé :

* `npm ci --include=dev --legacy-peer-deps` → PASS
* `npm run check` → PASS
* `npm run build` → PASS
* PostgreSQL Railway → structure contrôlée et cohérente
* Web actuel → conservé
* aucune modification applicative effectuée
* aucun Expo / React Native créé

Le seul blocage critique actuellement démontré lors du démarrage production est :

```text
REFRESH_TOKEN_SALT doit être défini en production avec une valeur stable.
```

D’autres variables de production doivent également être vérifiées, notamment celles liées à KMS et au stockage StreetView.

---

# OBJECTIF UNIQUE DE CETTE PHASE

Faire en sorte que **le BurkinaWatch backend actuel puisse réellement démarrer en mode production sur Railway**, sans modifier l’architecture applicative.

Cette phase est une phase de **configuration et de validation**, pas une phase de développement.

# ÉTAPE 3 — VÉRIFIER LES VARIABLES DE PRODUCTION

Vérifie dans le **service Railway de production**, sans jamais afficher les valeurs secrètes.

Contrôle au minimum :

```text
NODE_ENV
PORT
RAILWAY_DATABASE_URL
SESSION_SECRET
REFRESH_TOKEN_SALT
KMS_ENABLED
```

Puis vérifie la branche de chiffrement.

### Si :

```text
KMS_ENABLED=false
```

il faut vérifier la présence de :

```text
MASTER_ENCRYPTION_KEY
```

### Si :

```text
KMS_ENABLED=true
```

il faut vérifier :

```text
KMS_PROJECT_ID
KMS_LOCATION_ID
KMS_KEY_RING_ID
KMS_CRYPTO_KEY_ID
```

Ne modifie pas la valeur d’une clé existante.

Ne remplace jamais une clé secrète par une valeur arbitraire.

---

# ÉTAPE 4 — REFRESH_TOKEN_SALT

Le rapport Phase 1 a identifié ce blocage :

```text
REFRESH_TOKEN_SALT
```

Vérifie si cette variable existe réellement dans le service Railway de production.

Si elle est absente :

* signale précisément que c’est le blocage actuel ;
* si tu as réellement accès aux variables Railway et que la procédure permet de créer la variable sans exposer sa valeur, configure-la avec une valeur cryptographiquement aléatoire et stable ;
* ne l’affiche jamais ;
* ne la committe jamais ;
* ne la place dans aucun fichier du dépôt ;
* ne génère pas une nouvelle valeur à chaque démarrage.

**IMPORTANT :**

Si tu n’as pas l’accès permettant de créer/modifier le secret Railway de manière sûre, ne contourne pas le problème dans le code.

Dans ce cas, ARRÊTE-TOI et indique simplement :

```text
ACTION MANUELLE REQUISE DANS RAILWAY
```

Vérifie également les paramètres optionnels nécessaires au fournisseur utilisé.

Ne teste pas avec des clés inventées.

Ne remplace pas le système de stockage.

Ne migre aucun fichier.

Ne modifie aucune donnée StreetView.

Si la configuration S3 n’est pas disponible, signale :

```text
STREETVIEW PRODUCTION STORAGE = NON VALIDÉ
```

et explique précisément l’action manuelle nécessaire.

# ÉTAPE 8 — VALIDATION DU DÉMARRAGE PRODUCTION

Le test de démarrage ne doit plus s’arrêter sur :

```text
REFRESH_TOKEN_SALT
```

Vérifie que :

```text
server.listen()
```

est effectivement atteint.

Vérifie ensuite :

* que le processus reste actif ;
* qu’il n’entre pas en crash loop ;
* qu’il écoute sur le port Railway ;
* qu’il écoute sur `0.0.0.0`.

# ÉTAPE 9 — TEST HTTP RÉEL

Une fois le service déployé, teste le domaine public Railway réel.

Vérifie au minimum :

```text
GET /
```

et :

```text
GET /api/stats
```

Objectif :

```text
HTTP 200
```

Dans ce cas, teste un endpoint public approprié et documente lequel.
