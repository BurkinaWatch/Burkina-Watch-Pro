Nous validons une nouvelle orientation stratégique pour le projet Street View 3D de BurkinaWatch.

IMPORTANT :

Nous ne voulons plus bloquer le développement de Street View en attendant un GPU cloud.

Le GPU devient une infrastructure d'accélération future, et NON une dépendance obligatoire du produit.

La stratégie est désormais :

PLATEFORME STREET VIEW COMPLÈTE
+
PIPELINE CPU-FIRST
+
RECONSTRUCTION ENGINE ABSTRAIT
+
GPU AJOUTABLE PLUS TARD

Cette phase doit donc permettre de continuer le développement sans GPU.

==================================================

1. OBJECTIF DE LA PHASE
   ==================================================

Construire et/ou préparer l'architecture permettant à BurkinaWatch de gérer de véritables contributions Street View :

Utilisateur
→ capture vidéo
→ métadonnées
→ géolocalisation
→ upload sécurisé
→ stockage
→ validation
→ file de traitement
→ préparation CPU
→ tentative de reconstruction
→ scène 3D lorsque le moteur est disponible
→ publication.

Le système doit fonctionner même si aucun GPU n'est disponible.

Il ne faut jamais créer de faux résultats 3D pour masquer l'absence de moteur.

5. STOCKAGE
===========

Les vidéos originales doivent rester hors PostgreSQL.

La base doit conserver uniquement :

* métadonnées ;
* identifiants ;
* références de fichiers ;
* statuts ;
* résultats ;
* relations.

Conserver une organisation logique du type :

streetview/
originals/
thumbnails/
keyframes/
processing/
scenes/
exports/

Ne pas créer de duplication inutile du stockage.

Respecter l'architecture de stockage déjà présente si elle est correcte.

Burkina Faso

7. DIMENSION TEMPORELLE
=======================

Une même zone doit pouvoir être capturée plusieurs fois.

Exemple :

Rue X
├── capture 2026
├── capture 2027
├── capture 2028
└── capture 2030

Ne jamais remplacer automatiquement une ancienne capture.

Les différentes versions temporelles doivent pouvoir coexister.

Prévoir cette logique dans le modèle de données.

==================================================
8. RECONSTRUCTION ENGINE
========================

C'est le point architectural central de cette phase.

Créer ou préparer une abstraction conceptuelle :

ReconstructionEngine

Elle ne doit pas être liée directement à COLMAP ou à un fournisseur GPU.

Elle doit pouvoir recevoir une contribution préparée et produire des artefacts de reconstruction.

Conceptuellement :

ReconstructionEngine
│
├── CpuReconstructionEngine
│
└── GpuReconstructionEngine (futur)

Le système actuel peut utiliser :

CpuReconstructionEngine

Le futur système pourra utiliser :

GpuReconstructionEngine

sans modifier le reste de BurkinaWatch.

IMPORTANT :

Ne pas implémenter un faux GpuReconstructionEngine.

Le moteur GPU futur doit être clairement marqué comme non disponible tant qu'il n'existe pas réellement.

==================================================
9. CPU-FIRST
============

Déterminer ce qui peut réellement être effectué sur CPU.

Priorité :

1. validation vidéo ;
2. extraction des métadonnées ;
3. génération de miniature ;
4. extraction d'images/keyframes ;
5. analyse qualité ;
6. préparation des images ;
7. éventuellement SfM CPU ;
8. éventuellement MVS CPU sur de petits datasets.

Ne pas promettre des performances irréalistes.

Mesurer réellement les performances lorsqu'un calcul est exécuté.

==================================================
10. COLMAP CPU
==============

Étudier précisément si COLMAP peut être utilisé dans l'environnement actuel en mode CPU.

Ne pas contourner les protections de l'environnement pour forcer une installation dangereuse.

Ne pas utiliser :

NIXPKGS_ALLOW_INSECURE=1

simplement pour faire fonctionner une dépendance bloquée.

Si COLMAP n'est pas installable proprement dans l'environnement actuel :

documenter le problème.

Prévoir une méthode reproductible alternative pour un environnement CPU dédié, sans toucher à la production.

Par exemple :

Docker
ou
runner CPU dédié.

Ne pas prétendre qu'une reconstruction fonctionne si elle n'a pas réellement été exécutée.

==================================================
12. JOBS
========

Réutiliser le système de jobs actuel.

Prévoir des jobs idempotents.

Un job ne doit pas produire plusieurs scènes identiques lorsqu'il est relancé.

Prévoir :

* attempts ;
* maxAttempts ;
* progress ;
* errorCode ;
* errorMessage ;
* startedAt ;
* completedAt ;
* retry ;
* timeout ;
* lease/locking si déjà présent.

Ne jamais afficher un pourcentage fictif.

==================================================
13. LIMITATION CPU
==================

Le système doit savoir reconnaître qu'une reconstruction est trop lourde pour le CPU.

Par exemple :

* trop d'images ;
* résolution excessive ;
* durée excessive ;
* mémoire insuffisante ;
* temps estimé excessif.

Dans ce cas, ne pas bloquer indéfiniment le worker.

Le job doit pouvoir passer à un état du type :

WAITING_FOR_GPU

ou

DEFERRED_FOR_GPU

si cette notion est compatible avec l'architecture existante.

Cela permettra plus tard :

CPU → GPU

sans refaire toute la plateforme.
