==================================================
1. MODÈLE DE DONNÉES
==================================================

Ajoute uniquement les entités nécessaires à la fonctionnalité, en respectant le système ORM/schema existant.

Le modèle doit permettre de représenter au minimum :

A. VISITE / PRÉSENCE

Une présence potentielle de l’utilisateur dans un lieu.

Elle doit pouvoir contenir, selon les besoins réels du projet :
- utilisateur ;
- lieu ;
- début de présence ;
- dernière activité/localisation pertinente ;
- durée estimée ;
- statut ;
- déclenchement ou non du check-in ;
- date de création.

Ne conserve pas inutilement un historique GPS détaillé.

B. EXPÉRIENCE DU LIEU

Enregistrement de la perception déclarée par l’utilisateur.

Valeurs :
- SAFE / sécurité ressentie ;
- UNCERTAIN / incertain ;
- UNSAFE / pas en sécurité.

Prévoir éventuellement :
- catégories de raisons ;
- commentaire facultatif ;
- lieu concerné ;
- date/heure ;
- contexte minimal nécessaire ;
- statut de traitement.

Ne transforme jamais automatiquement UNSAFE en « incident confirmé ».

Une perception subjective de sécurité est différente d’un signalement d’incident.

C. CANDIDAT DE LIEU

Permettre de proposer un nouveau lieu.

Champs selon architecture existante :
- nom ;
- catégorie ;
- description ;
- latitude ;
- longitude ;
- photo/média ;
- utilisateur contributeur ;
- date ;
- statut de modération ;
- lieu existant éventuellement associé ;
- source/contribution.

Statuts recommandés :
- PENDING
- APPROVED
- REJECTED
- DUPLICATE

D. CONFIGURATION DU DÉLAI

Le délai avant déclenchement du check-in doit être configurable.

NE PAS inscrire dans le code une valeur présentée comme scientifiquement universelle.

Utilise la valeur recommandée par l’audit comme valeur initiale si elle est techniquement pertinente, mais rends-la configurable.

==================================================
2. DÉTECTION « NOUVEAU LIEU »
==================================================

Réutilise le système de lieux existant.

Ne crée surtout pas une deuxième base de lieux.

La logique doit déterminer si la zone correspond :
- à un lieu existant ;
- à un lieu déjà visité par l’utilisateur ;
- à un lieu nouveau/candidat.

Prévois une tolérance géographique raisonnable afin de ne pas générer plusieurs lieux pour quelques mètres de différence GPS.

==================================================
3. DÉTECTION DE PRÉSENCE
==================================================

La fonctionnalité ne doit pas se déclencher simplement parce que le GPS indique une nouvelle position.

Évite les déclenchements lorsque l’utilisateur :
- marche rapidement ;
- roule ;
- est en transit ;
- traverse simplement une zone.

Lorsque les capacités techniques existantes le permettent, utilise des signaux tels que :
- stabilité de position ;
- durée dans la zone ;
- activité/déplacement ;
- vitesse estimée ;
- présence continue.

Si le Web ne permet pas une détection fiable en arrière-plan, NE SIMULE PAS cette capacité.

Implémente proprement ce qui est réellement possible et prépare une architecture compatible avec le Mobile si celui-ci possède les capacités nécessaires.

==================================================
4. OPT-IN
==================================================

La fonctionnalité doit être explicitement activée par l’utilisateur.

Conditions minimales :
- notifications push activées ;
- permission de localisation nécessaire accordée ;
- préférence « Expérience du lieu » activée.

Si une permission manque :
- ne pas déclencher ;
- ne pas contourner la permission ;
- ne pas tenter de collecter clandestinement la localisation.
