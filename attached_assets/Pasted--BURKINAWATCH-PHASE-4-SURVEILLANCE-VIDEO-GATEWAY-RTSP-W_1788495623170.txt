# BURKINAWATCH — PHASE 4

## SURVEILLANCE — VIDEO GATEWAY + RTSP → WEBRTC

Tu travailles sur **BurkinaWatch**.

Les phases précédentes ont préparé :

* la sécurité générale de l'application ;
* l'authentification et l'autorisation ;
* la protection IDOR ;
* la protection SSRF ;
* le chiffrement AES-256-GCM ;
* le modèle applicatif des caméras ;
* la gestion sécurisée des credentials ;
* la structure frontend de Surveillance.

Cette phase a pour objectif d'étudier et de préparer l'intégration du **transport vidéo réel**.

Architecture cible :

```text
                 BURKINAWATCH

Utilisateur
     │
     ▼
Frontend
     │
 HTTPS/WebRTC
     │
     ▼
Backend Express
     │
     │ contrôle / autorisation
     ▼
VIDEO GATEWAY
     │
     │ RTSP
     ▼
CAMÉRA IP
```

Le Backend Express est le **control plane**.

Le Video Gateway est le **media plane**.

NE FAIS PAS transiter la vidéo elle-même à travers Express.

---

# ⚠️ RÈGLES ABSOLUES

Cette phase doit être exécutée progressivement.

NE PAS :

* exposer une caméra RTSP directement sur Internet ;
* demander à l'utilisateur d'ouvrir le port 554 sur son routeur ;
* désactiver un firewall ;
* créer une route Express qui proxifie continuellement la vidéo ;
* transmettre le flux vidéo dans PostgreSQL ;
* stocker des fichiers vidéo ;
* utiliser une URL RTSP publique contenant username/password ;
* mettre des credentials dans le frontend ;
* mettre des credentials dans Git ;
* mettre des credentials dans les logs ;
* déployer une infrastructure vidéo en production sans validation ;
* utiliser une vraie caméra si les tests préalables ne sont pas concluants.

NE PAS implémenter :

* enregistrement ;
* replay ;
* IA ;
* reconnaissance faciale ;
* détection intelligente ;
* alertes ;
* snapshots automatiques.

Cette phase concerne uniquement :

**LIVE VIDEO.**

# 4. PROBLÈME NAT / CGNAT

C'est l'un des points les plus importants.

Une caméra peut être derrière :

* box internet ;
* routeur ;
* réseau privé ;
* 4G ;
* 5G ;
* CGNAT ;
* firewall.

Donc l'architecture suivante est INTERDITE comme architecture générale :

```text
Internet
   ↓
IP publique utilisateur
   ↓
port 554
   ↓
caméra
```

Ne demande jamais à l'utilisateur d'exposer directement sa caméra.

---

Évalue sérieusement :

```text
BURKINAWATCH VIDEO GATEWAY
```

* éventuellement routeur compatible.

Mais :

**NE DÉVELOPPE PAS encore cet agent.**

Détermine seulement s'il est nécessaire.

```text
      ↓
```

# 7. IDENTIFICATION DU FLUX

Le système doit éviter d'utiliser :

```text
rtsp://username:password@host:554/path
```

dans le frontend.

Préférer :

```text
cameraId
```

Le backend/gateway doit connaître la configuration réelle.

---

# 8. AUTHENTIFICATION DU FLUX

Conçois le mécanisme :

```text
Utilisateur connecté
        ↓
GET /api/surveillance/cameras/:id/live
        ↓
Backend vérifie :
    authentification
    ownership
    caméra active
        ↓
autorisation temporaire
        ↓
Video Gateway
        ↓
WebRTC
```

Le navigateur ne doit jamais recevoir le mot de passe caméra.

---

# 9. TOKENS

Conçois un système de token temporaire.

Le token doit idéalement être :

* court ;
* limité à une caméra ;
* limité à un utilisateur ;
* expirant ;
* non réutilisable si possible ;
* impossible à deviner.

Exemple conceptuel :

```text
userId
cameraId
expiration
nonce
```

Le token ne doit pas être un simple :

```text
cameraId
```

---

# 10. IDOR

Tester obligatoirement :

```text
User A
   ↓
Camera A
   ↓
Live A
   ↓
PASS
```

mais :

```text
User A
   ↓
Camera B
   ↓
Live B
   ↓
REFUS
```

Tester :

* GET caméra ;
* live ;
* token ;
* accès gateway ;
* modification ;
* suppression.

---

# 11. VIDEO GATEWAY

Si MediaMTX est retenu, définir une architecture logique du type :

```text
BurkinaWatch Backend
        │
        │ API sécurisée
        ▼
MediaMTX
        │
        ├── camera-userA-001
        ├── camera-userA-002
        ├── camera-userB-001
        └── ...
```

Les paths ne doivent pas être prédictibles de manière exploitable.

Ne pas exposer inutilement l'API administrative de MediaMTX à Internet.

---

# 12. ISOLATION DES CAMÉRAS

Une caméra doit être isolée logiquement.

Exemple :

```text
camera-A
camera-B
```

Un utilisateur ayant accès à A ne doit jamais pouvoir deviner ou utiliser le path de B.

Ne compte pas uniquement sur l'obscurité du path.

L'autorisation doit être vérifiée côté serveur/gateway.

---

# 13. WEBRTC

Évalue les exigences réelles :

* signaling ;
* ICE ;
* STUN ;
* TURN ;
* NAT traversal ;
* HTTPS ;
* certificats ;
* ports UDP ;
* fallback TCP/TLS si nécessaire ;
* compatibilité Chrome ;
* compatibilité Android ;
* compatibilité iOS.

Ne déploie pas TURN tant que le besoin n'est pas démontré.

# 14. TURN

Explique précisément quand TURN devient nécessaire.

Architecture possible :

```text
Browser
   │
   ├── STUN → connexion directe
   │
   └── TURN → relais si nécessaire
```

Détermine :

* si un serveur TURN sera nécessaire pour le MVP ;
* où il pourrait être hébergé ;
* coûts ;
* bande passante ;
* sécurité.

Ne déploie rien pour le moment.

# 15. HTTPS

Vérifie :

* HTTPS ;
* WebRTC secure context ;
* CSP ;
* CORS ;
* origins ;
* domaines autorisés.

Ne désactive jamais la sécurité navigateur simplement pour faire fonctionner le prototype.

# 16. CSP

Vérifie la Content Security Policy actuelle.

Détermine ce qu'il faudra éventuellement autoriser pour :

* WebRTC ;
* Video Gateway ;
* MediaMTX ;
* WebSocket/signaling si nécessaire.

Ne remplace pas toute la CSP par :

```text
*
```

ou une politique permissive.

---

# 17. CORS

Le gateway ne doit pas accepter :

```text
Access-Control-Allow-Origin: *
```

pour des flux authentifiés.

Définis les origins autorisés.

# 21. CODECS

Vérifie les codecs réellement supportés.

Une caméra peut fournir :

* H.264
* H.265
* MJPEG

WebRTC n'accepte pas nécessairement tous les flux directement.

Détermine si transcoding sera nécessaire.

Attention :

Le transcoding peut multiplier fortement la consommation CPU.

---

# 22. RTSP / ONVIF

RTSP et ONVIF ont des rôles différents.

Ne les confonds pas.

Évaluer :

### ONVIF

Pour :

* découverte ;
* identification ;
* configuration ;
* contrôle éventuel.

### RTSP

Pour :

* transport du flux vidéo.

Pour le MVP :

RTSP peut être le mécanisme principal de transport.

ONVIF pourra être ajouté plus tard.

---

# 23. NE PAS FAIRE DE SCAN RÉSEAU

Le backend BurkinaWatch ne doit pas scanner automatiquement :

```text
192.168.0.1 → 192.168.0.255
```

ou d'autres plages privées.

Ne tente pas de découvrir automatiquement des caméras sur les réseaux internes depuis le cloud.

Cela créerait des risques SSRF et d'abus réseau.

---

# 24. SSRF

Réutiliser les protections existantes.

Ne jamais permettre à un utilisateur de transformer BurkinaWatch en scanner réseau.

Toute connexion vers une caméra doit être :

* explicitement associée à une caméra enregistrée ;
* autorisée ;
* limitée ;
* contrôlée ;
* journalisée sans secrets.

---

# 25. LOGS

Ne jamais logger :

```text

```

ni :

```text
Authorization: Bearer ...
```

ni :


ni :

```text
WebRTC credentials
```

ni :


Utiliser les redactions existantes.
