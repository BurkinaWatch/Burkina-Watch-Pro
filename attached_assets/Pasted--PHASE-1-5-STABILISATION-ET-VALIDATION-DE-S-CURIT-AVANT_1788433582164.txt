# PHASE 1.5 — STABILISATION ET VALIDATION DE SÉCURITÉ AVANT SURVEILLANCE

Tu vas maintenant effectuer une phase de stabilisation technique de Burkina Watch avant toute conception ou implémentation du module « Surveillance ».

## OBJECTIF

L'objectif est de rendre la base actuelle suffisamment saine pour pouvoir ensuite ajouter un système de vidéosurveillance privée sans construire sur des incohérences existantes.

Cette phase est UNIQUEMENT une phase de correction, d'audit et de validation.

## INTERDICTIONS ABSOLUES

NE PAS :

* créer le module Surveillance ;
* créer un modèle Camera ;
* créer des routes `/surveillance` ;
* installer MediaMTX ;
* installer FFmpeg ;
* installer/configurer WebRTC ;
* configurer RTSP ;
* connecter une caméra réelle ;
* créer du streaming vidéo ;
* créer de l'enregistrement vidéo ;
* créer de l'IA vidéo ;
* modifier l'architecture générale de Burkina Watch ;
* remplacer Passport/session ;
* remplacer PostgreSQL ;
* remplacer Drizzle ;
* effectuer un reset de base ;
* utiliser `db:push` de manière aveugle ;
* supprimer des tables ;
* supprimer des données ;
* effectuer une migration destructive ;
* modifier directement la production Railway.

NE TOUCHE PAS AUX FONCTIONNALITÉS MÉTIER SI CE N'EST PAS NÉCESSAIRE À LA SÉCURITÉ.

La priorité absolue est :

> NE RIEN CASSER.

# 3. AUDIT DES AUTORISATIONS EXISTANTES

Nous avons maintenant les helpers :

```text
requireAuthenticatedUser()
requireRole()
requireResourceOwnership()
requirePermission()
getAuthenticatedUserId()
getAuthenticatedPrincipal()
```

Ne refactore pas immédiatement tout le dépôt.

Commence par rechercher les routes qui manipulent des ressources appartenant à un utilisateur.

Exemples :

* signalements ;
* profils ;
* notifications ;
* alertes ;
* tracking ;
* données privées ;
* contacts ;
* ressources administratives ;
* toute ressource identifiée par un ID.

Pour chaque route sensible, vérifie :

```text
Utilisateur authentifié ?
        ↓
Ressource demandée ?
        ↓
Propriétaire vérifié ?
        ↓
Permission/rôle vérifié ?
        ↓
Accès autorisé ?
```

Cherche spécifiquement les patterns dangereux :

```text
GET /resource/:id
PATCH /resource/:id
PUT /resource/:id
DELETE /resource/:id
POST avec resourceId
```

où l'ID est utilisé directement sans vérification du propriétaire.

Cherche également les risques d'IDOR :

```text
userId
ownerId
createdBy
reportId
alertId
trackingId
notificationId
```

NE SUPPOSE PAS qu'un ID suffit à autoriser l'accès.

Pour chaque problème trouvé :

* corrige uniquement si la correction est claire et non destructive ;
* utilise les helpers centralisés ;
* conserve les comportements métier existants ;
* ne fais pas une refonte globale.

Ajoute au minimum des tests d'isolation pour démontrer :

```text
Utilisateur A ne peut pas lire la ressource privée de B.
Utilisateur A ne peut pas modifier la ressource privée de B.
Utilisateur A ne peut pas supprimer la ressource privée de B.
```

# 8. AUDIT FINAL SPÉCIFIQUE À LA FUTURE SURVEILLANCE

Sans créer Surveillance, vérifie que l'architecture actuelle permettra ultérieurement de respecter ces principes :

```text
Compte utilisateur
      ↓
Caméra appartenant à cet utilisateur
      ↓
Permission explicite
      ↓
Session vidéo temporaire
      ↓
Media Gateway séparée
      ↓
Flux vidéo
```

Le backend Express ne devra PAS devenir le transporteur du flux vidéo.

Les credentials caméra ne devront jamais être exposés au frontend.

Les URLs RTSP ne devront jamais être envoyées au navigateur.

Aucune caméra ne devra être directement exposée sur Internet simplement pour permettre la connexion.

Cette phase ne doit cependant créer aucun composant vidéo.
