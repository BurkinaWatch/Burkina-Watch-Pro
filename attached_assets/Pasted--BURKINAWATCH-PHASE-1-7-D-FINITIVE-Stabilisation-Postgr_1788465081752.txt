# BURKINAWATCH — PHASE 1.7 DÉFINITIVE

## Stabilisation PostgreSQL Railway + migrations + secrets + chiffrement

### AVANT TOUT DÉVELOPPEMENT DE LA FONCTION SURVEILLANCE

Tu travailles sur le projet BurkinaWatch.

Cette phase est une phase de **REMÉDIATION ET STABILISATION**, pas une phase de développement fonctionnel.

## OBJECTIF PRINCIPAL

La décision d'architecture est maintenant définitive :

> **RAILWAY POSTGRESQL EST LA SEULE BASE DE DONNÉES DE PRODUCTION DE BURKINAWATCH.**

Il ne faut plus maintenir une ambiguïté entre plusieurs bases PostgreSQL.

Architecture cible :

```text
BURKINAWATCH
     │
     ├── Frontend React/Vite
     │
     ├── Backend Node.js / Express / TypeScript
     │
     ├── Drizzle ORM
     │
     └── PostgreSQL RAILWAY
              │
              └── SOURCE DE VÉRITÉ PRODUCTION
```

Replit sert au développement et au déploiement du code.

Railway héberge la base PostgreSQL de production.

L'application de production ET Drizzle doivent travailler avec la même base Railway.

# ÉTAPE 2 — RAILWAY POSTGRESQL = SOURCE DE VÉRITÉ

La base PostgreSQL Railway existante est la base de production de référence.

Le code doit être aligné sur cette décision.

Objectif :

```text

       ↓

Drizzle
       ↓
PostgreSQL Railway
```

```text
Backend → DB A
Drizzle → DB B
```

### IMPORTANT

Tu dois corriger la configuration pour que le backend et Drizzle utilisent une configuration cohérente.

Privilégie une variable standard :

```text

```

pour la connexion PostgreSQL de production.

Si Railway fournit déjà une variable spécifique ou une référence interne, utilise-la de manière sécurisée via la configuration d'environnement Railway, mais évite de conserver une logique ambiguë avec deux bases concurrentes.

NE COPIE JAMAIS la valeur réelle de la DATABASE_URL dans le code.

NE L'AFFICHE JAMAIS.

NE LA COMMIT PAS.

Le dépôt contient actuellement plusieurs fichiers de migration historiques.

Ne suppose PAS que leur historique reflète exactement l'état réel de Railway.

```text

```

Le but est de construire une stratégie de migration fiable à partir de l'état actuel de Railway.

### RÈGLE

La base Railway existante contient déjà des données importantes.

Donc :

> **L'état réel de Railway doit être préservé.**

Si nécessaire, prépare une baseline Drizzle contrôlée correspondant à l'état actuel, sans recréer les tables existantes.

Ne lance aucune commande destructive.

Ne lance jamais :

```text

```

ou :

```text

```

ou toute commande équivalente sur production.

# ÉTAPE 8 — REFRESH_TOKEN_SALT

Le système de hash des refresh tokens doit utiliser un secret stable.

Il est INTERDIT d'avoir un fallback du type :

```text

```

en production.

La configuration production doit exiger :

```text
REFRESH_TOKEN_SALT
```

avec une valeur stable et suffisamment robuste.

Si elle est absente en production :

> le backend doit refuser de démarrer.

NE JAMAIS afficher la valeur dans le rapport.

NE JAMAIS demander à l'utilisateur de la mettre dans le code.

Elle doit être configurée dans le gestionnaire de secrets Railway/Replit approprié.
