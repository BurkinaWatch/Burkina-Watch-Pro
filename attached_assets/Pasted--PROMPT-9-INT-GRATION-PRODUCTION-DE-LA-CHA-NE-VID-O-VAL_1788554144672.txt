# 4. INTÉGRATION CAMERA AGENT

Le Camera Agent doit être considéré comme un composant indépendant.

Il doit :

* s'authentifier ;
* maintenir son identité ;
* établir sa connexion sécurisée ;
* communiquer avec le système média ;
* publier le flux autorisé ;
* détecter les pertes de connexion ;
* reconnecter proprement ;
* envoyer son heartbeat ;
* signaler son état ;
* respecter les bindings autorisés.

Il ne doit PAS :

* accéder directement à PostgreSQL ;
* posséder `DATABASE_URL` ;
* posséder `MASTER_ENCRYPTION_KEY` ;
* posséder les secrets globaux du backend ;
* exposer une interface d'administration publique ;
* permettre l'exécution arbitraire de commandes ;
* scanner le réseau local ;
* modifier la configuration de BurkinaWatch.

---

# 5. IDENTITÉ DU CAMERA AGENT

Chaque Camera Agent doit avoir une identité unique.

Vérifier :

* `agentId` ;
* credentials ou token d'agent ;
* expiration si applicable ;
* rotation ;
* révocation ;
* état actif/inactif ;
* dernière connexion ;
* dernier heartbeat ;
* version de l'agent.

Le serveur doit pouvoir :

* enregistrer un agent ;
* l'autoriser ;
* le révoquer ;
* détecter son absence ;
* accepter sa reconnexion ;
* empêcher un agent révoqué de publier.

---

# 6. ENROLLMENT SÉCURISÉ

Vérifier le mécanisme d'enrollment.

Le système doit éviter :

* secrets permanents affichés en clair ;
* credentials stockés en clair ;
* tokens réutilisables indéfiniment ;
* enrollment sans expiration ;
* enrollment sans révocation.

Si un code d'enrollment existe :

* il doit être limité dans le temps ;
* à usage limité ;
* lié au contexte prévu ;
* invalidé après utilisation ;
* absent des logs.

NE PAS afficher les secrets complets dans l'interface utilisateur après leur création.

---

# 7. ASSOCIATION AGENT ↔ CAMÉRA

Vérifier qu'une caméra ne peut être publiée que par l'agent autorisé.

Relation logique :

USER
↓
CAMERA
↓
AUTHORIZED CAMERA AGENT
↓
STREAM

Un agent A ne doit jamais pouvoir publier le flux de la caméra B sans autorisation.

Tester explicitement :

* agent correct → caméra correcte ;
* agent correct → mauvaise caméra ;
* agent révoqué → caméra ;
* agent d'un autre utilisateur → caméra ;
* caméra supprimée → publication ;
* caméra désactivée → publication.

Tous les cas non autorisés doivent être refusés.

---

# 8. IDENTITÉ DU STREAM

Chaque flux doit avoir une identité déterministe.

Par exemple :

`streamId`

ou une combinaison sécurisée :

`agentId + cameraId + streamId`

NE PAS utiliser :

* nom de caméra fourni directement par l'utilisateur ;
* chemin RTSP arbitraire ;
* identifiant pouvant être injecté ;
* valeur permettant de deviner les flux d'autres utilisateurs.

Les identifiants média ne doivent pas révéler inutilement :

* userId ;
* email ;
* credentials ;
* IP privée ;
* RTSP URL.

---

# 9. PROTECTION CONTRE L'IDOR

Auditer absolument toutes les routes liées à :

* cameras ;
* camera agents ;
* streams ;
* viewer sessions ;
* tokens ;
* status ;
* configuration ;
* suppression ;
* modification ;
* association agent/caméra.

Tester :

Utilisateur A :

* GET caméra B ;
* PUT caméra B ;
* DELETE caméra B ;
* start stream B ;
* stop stream B ;
* obtenir token B ;
* obtenir status B ;
* créer viewer session B.

Tout doit être refusé.

Ne jamais faire confiance à :

* `userId` envoyé par le frontend ;
* `cameraId` seul ;
* `agentId` seul ;
* paramètres URL ;
* données JSON ;
* headers contrôlés par le client.

L'autorisation doit être déterminée côté serveur.

---

# 10. CREDENTIALS CAMÉRA

Les credentials RTSP/ONVIF doivent rester secrets.

Vérifier :

* chiffrement AES-256-GCM ;
* clé maître fournie par environnement sécurisé ;
* IV unique ;
* authentication tag ;
* absence de plaintext en DB ;
* absence dans les logs ;
* absence dans les réponses API ;
* absence dans les URLs frontend.

Le frontend ne doit jamais recevoir :

* mot de passe caméra ;
* RTSP URL complète ;
* credentials ONVIF ;
* master key ;
* secrets MediaMTX.

---

# 11. FLUX RTSP

Le RTSP doit rester dans le périmètre backend/agent/gateway.

Le navigateur ne doit jamais faire :

`browser → rtsp://...`

Le navigateur doit faire uniquement :

`browser → authenticated WebRTC/WHEP`

Vérifier le code frontend et supprimer toute éventuelle exposition RTSP.

# 13. TOKEN DE VISIONNAGE

Le token permettant d'accéder au flux doit être :

* court ;
* temporaire ;
* signé ;
* lié à l'utilisateur ;
* lié à la caméra ;
* lié au stream ;
* vérifié côté serveur ;
* révocable si nécessaire.

Ne jamais utiliser :

* token permanent ;
* token global pour toutes les caméras ;
* token basé uniquement sur cameraId ;
* token stocké inutilement dans localStorage.

Tester :

* token valide ;
* token expiré ;
* token modifié ;
* token d'une autre caméra ;
* token d'un autre utilisateur ;
* token après révocation.

# 21. RÉSEAU

L'architecture doit respecter :

`CAMERA → AGENT → OUTBOUND SECURE CONNECTION`

et non :

`INTERNET → CAMERA RTSP`

INTERDICTION de demander à l'utilisateur :

* ouvrir le port 554 ;
* exposer RTSP sur Internet ;
* mettre la caméra en DMZ ;
* désactiver le firewall ;
* activer UPnP pour contourner la sécurité.

# 22. SSRF

Toutes les URLs fournies par l'utilisateur ou utilisées pour connecter une caméra doivent continuer à bénéficier de la protection SSRF déjà mise en place.

Bloquer notamment :

* localhost ;
* loopback ;
* private IPv4 ;
* private IPv6 ;
* link-local ;
* metadata endpoints ;
* multicast ;
* schémas non autorisés ;
* credentials dans URL.

Attention aux contournements :

* DNS rebinding ;
* IPv4 encodé ;
* IPv6 ;
* decimal IP ;
* octal ;
* redirects ;
* hostname ambigu ;
* résolution DNS différente.

Ne pas désactiver la protection SSRF pour faire fonctionner une caméra.
