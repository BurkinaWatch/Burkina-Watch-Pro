# PHASE 1.6 — POSTGRESQL, DRIZZLE, SECRETS ET CHIFFREMENT

Nous allons maintenant effectuer une phase strictement limitée à la fiabilisation de la base de données, des migrations, des secrets et du système de chiffrement de Burkina Watch.

Cette phase est un PRÉREQUIS avant toute implémentation de Surveillance.

## OBJECTIF

À la fin de cette phase, nous devons avoir une compréhension exacte et documentée de :

1. la base PostgreSQL réellement utilisée par l'application ;
2. la base utilisée par Drizzle ;
3. l'état réel du schéma ;
4. l'état réel des migrations ;
5. les divergences éventuelles ;
6. les secrets qui doivent être présents en production ;
7. l'état réel du système de chiffrement ;
8. les corrections nécessaires pour pouvoir stocker ultérieurement des credentials de caméras de manière sécurisée.

---

# INTERDICTIONS ABSOLUES

NE PAS :

* créer le module Surveillance ;
* créer de table `Camera` ;
* créer de route Surveillance ;
* créer RTSP ;
* créer WebRTC ;
* installer MediaMTX ;
* installer FFmpeg ;
* connecter une caméra ;
* créer un serveur vidéo ;
* créer de l'enregistrement ;
* créer de l'IA vidéo ;
* modifier l'architecture générale ;
* remplacer PostgreSQL ;
* remplacer Drizzle ;
* remplacer Passport/session ;
* supprimer des tables ;
* supprimer des données ;
* effectuer `DROP DATABASE` ;
* effectuer `DROP TABLE` ;
* effectuer un reset ;
* exécuter `db:push` automatiquement ;
* exécuter une migration destructive ;
* modifier directement la base de production sans validation explicite.

Aucune opération destructive n'est autorisée.

---

# PARTIE 1 — CARTOGRAPHIE DES BASES

Commence par déterminer précisément les connexions utilisées.

Inspecte sans jamais afficher les valeurs secrètes :

```text
DATABASE_URL
RAILWAY_DATABASE_URL
```

Détermine :

```text
Application runtime
        ↓
Quelle variable ?
        ↓
Quelle base ?
```

et :

```text
Drizzle
        ↓
Quelle variable ?
        ↓
Quelle base ?
```

Pour chaque base accessible, relève uniquement :

* host sous forme anonymisée ;
* nom de base sous forme anonymisée ;
* environnement estimé ;
* nombre de tables ;
* présence ou absence de `__drizzle_migrations` ;
* état du schéma.

NE JAMAIS afficher :

* mot de passe ;
* URL complète ;
* credentials ;
* tokens ;
* secrets.

---

# PARTIE 2 — ÉTAT RÉEL DU SCHÉMA

Inspecte le schéma PostgreSQL en lecture seule.

Compare :

```text
schema Drizzle
        VS
tables PostgreSQL réellement présentes
```

Identifie :

* tables manquantes ;
* colonnes manquantes ;
* colonnes supplémentaires ;
* index ;
* contraintes ;
* relations ;
* types ;
* clés étrangères.

Ne modifie rien pendant cette étape.

Produis une matrice :

```text
Objet | Drizzle | PostgreSQL | Migration correspondante | Écart
```

---

# PARTIE 3 — AUDIT DES MIGRATIONS

Analyse :

```text
migrations/0000_jazzy_shape.sql
migrations/0001_add_medias_column.sql
migrations/0002_add_online_sessions.sql
migrations/0003_fix_online_sessions_id.sql
```

et :

```text
journal __drizzle_migrations
```

Détermine précisément :

* quelles migrations sont réellement appliquées ;
* lesquelles sont enregistrées ;
* lesquelles ne le sont pas ;
* si les migrations SQL correspondent au schéma actuel ;
* si certaines modifications existent déjà dans la base malgré l'absence d'enregistrement.

IMPORTANT :

Une migration SQL existante ne signifie pas automatiquement qu'elle a été appliquée.

Ne fais aucune supposition.

---

# PARTIE 4 — SOURCE DE VÉRITÉ

À partir de l'analyse, propose une source de vérité unique.

Elle devra être clairement définie :

```text
PostgreSQL réel
+
schéma Drizzle
+
historique des migrations
```

Si une divergence existe, explique exactement laquelle.

Ne corrige pas encore automatiquement une divergence potentiellement dangereuse.

---

# PARTIE 5 — PLAN DE RÉCONCILIATION

Si des migrations doivent être réconciliées :

prépare un plan FORWARD-ONLY.

Le plan doit :

* préserver toutes les données ;
* ne pas supprimer les tables existantes ;
* ne pas recréer inutilement le schéma ;
* ne pas utiliser `db:push` comme solution automatique ;
* permettre de revenir en arrière par une migration corrective si nécessaire.

Si une migration SQL doit être créée :

prépare-la et montre son contenu pour validation.

NE L'APPLIQUE PAS à la production.

---

# PARTIE 6 — SECRETS

Effectue un audit des variables nécessaires au fonctionnement de production.

Vérifie notamment :

```text
SESSION_SECRET
REFRESH_TOKEN_SALT
MASTER_ENCRYPTION_KEY
KMS_ENABLED
KMS_PROJECT_ID
KMS_LOCATION_ID
KMS_KEY_RING_ID
KMS_CRYPTO_KEY_ID
```

Tu peux également identifier d'autres variables sensibles réellement utilisées par le code.

Pour chacune :

```text
Nom
Présente ?
Utilisée ?
Obligatoire en production ?
Stockée correctement ?
```

NE JAMAIS afficher la valeur.

Utilise uniquement :

```text
CONFIGURÉ
NON CONFIGURÉ
OPTIONNEL
OBLIGATOIRE
INUTILISÉ
```

# PARTIE 7 — ROTATION

Identifie les secrets qui ont pu être exposés historiquement.

NE JAMAIS afficher les anciennes valeurs.

Produis uniquement :

```text
Secret
Type
Exposition historique
Action recommandée
```

Exemple :

```text
DATABASE credential
Exposé historiquement
Rotation obligatoire
```

Ne fais pas apparaître les secrets dans le rapport.

Ne crée aucun secret dans Git.

Ne place aucun secret dans :

```text
.replit
Dockerfile
ARG
ENV versionné
source code
```

---

# PARTIE 8 — CHIFFREMENT

Inspecte complètement :

```text
server/encryptionService.ts
```

Détermine :

1. quel algorithme est utilisé ;
2. comment les données sont chiffrées ;
3. comment elles sont déchiffrées ;
4. où les clés sont récupérées ;
5. si le système dépend de KMS ;
6. si un fallback existe ;
7. dans quelles conditions le fallback est activé ;
8. si le fallback est acceptable pour la production ;
9. si le système peut être utilisé ultérieurement pour les credentials caméra.

IMPORTANT :

Nous ne voulons pas seulement savoir si le fichier existe.

Nous voulons savoir si le système est réellement utilisable en production.

---

# PARTIE 9 — KMS

Analyse la dépendance :

```text
@google-cloud/kms
```

Vérifie :

* version déclarée ;
* version verrouillée ;
* compatibilité avec Node actuellement utilisé ;
* pourquoi elle est absente de `node_modules` ;
* si elle est nécessaire au runtime ;
* si elle est uniquement utilisée pour certains tests.

NE change pas arbitrairement la version.

NE supprime pas KMS.

NE remplace pas KMS par une autre solution sans validation.

Si une installation est nécessaire, indique la commande exacte et les conséquences.

---

# PARTIE 10 — DERNIÈRE ERREUR TYPESCRIPT

Exécute :

```bash
npm run check
```

Analyse l'erreur restante.

Si elle est liée à `@google-cloud/kms`, confirme-le.

Ne masque pas l'erreur.

Ne désactive pas TypeScript pour la faire disparaître.

Ne modifie pas les règles TypeScript pour contourner le problème.

---

# PARTIE 11 — TESTS

Après les corrections sûres, exécute :

```bash
npm run check
npm run build
node --import tsx --test server/__tests__/phase1Security.test.ts
git diff --check
```

Si le système de chiffrement peut être testé sans credentials réels, ajoute/exécute un test approprié.

Ne mets jamais de vraie clé ou de vrai secret dans les tests versionnés.

---

# PARTIE 12 — PRÉPARATION POUR SURVEILLANCE

Sans créer Surveillance, vérifie que le système pourra ultérieurement stocker de manière sécurisée :

```text
camera username
camera password
camera address
gateway credentials
temporary video tokens
```

Les credentials caméra devront à terme être :

```text
jamais envoyés au frontend
jamais affichés dans les logs
jamais stockés en clair
jamais intégrés dans une URL exposée au navigateur
```

Pour cette phase, ne crée aucun modèle caméra.
