# PHASE 9.1 — PRE-FLIGHT, WAN/CGNAT ET VALIDATION MÉDIA END-TO-END

## CONTEXTE

La Phase 9 de BurkinaWatch est terminée avec le verdict :

**READY WITH CONDITIONS**

Les conditions restantes sont exactement les suivantes :

1. exécuter le preflight Railway en lecture seule ;
2. valider le réseau WAN/CGNAT réel ;
3. compléter les documents de Phase 9 ;
4. réaliser les tests d'intégration média de bout en bout.

Cette phase 9.1 a pour unique objectif de lever ces conditions.

IMPORTANT :

NE PAS commencer une nouvelle architecture.

NE PAS ajouter de nouvelles fonctionnalités.

NE PAS déployer en production.

NE PAS modifier inutilement l'infrastructure existante.

NE PAS contourner une mesure de sécurité pour faire fonctionner un test.

---

# 1. RÈGLE ABSOLUE : LECTURE SEULE POUR RAILWAY

Commencer par effectuer un preflight Railway entièrement en lecture seule.

NE PAS :

* modifier les variables ;
* modifier les services ;
* modifier les domaines ;
* modifier les ports ;
* modifier les volumes ;
* modifier PostgreSQL ;
* déclencher un déploiement ;
* redémarrer un service volontairement ;
* modifier le réseau ;
* modifier les secrets ;
* modifier les configurations de production.

Le preflight doit uniquement OBSERVER et RAPPORTER.

Créer :

`docs/PHASE_9_1_RAILWAY_PREFLIGHT.md`

`db:push`

# 4. VALIDATION WAN / CGNAT

La deuxième condition doit être testée avec un réseau réellement distant.

Architecture à tester :

CAMÉRA IP
↓
RÉSEAU DISTANT
↓
NAT / CGNAT éventuel
↓
CAMERA AGENT
↓
CONNEXION SORTANTE SÉCURISÉE
↓
MEDIA GATEWAY
↓
WEBRTC/WHEP
↓
BURKINAWATCH

Le test doit idéalement être réalisé avec :

* réseau mobile ;
* hotspot ;
* connexion résidentielle ;
* ou autre réseau réellement différent de celui du serveur.

Si le réseau utilise un CGNAT, le constater et le documenter.

---

# 5. IMPORTANT : NE PAS EXPOSER LA CAMÉRA

Pour effectuer le test WAN :

NE PAS demander de :

* port forwarding RTSP ;
* port 554 ouvert sur Internet ;
* DMZ ;
* UPnP ;
* désactivation firewall ;
* exposition directe de la caméra.

Le principe doit rester :

`CAMÉRA → CAMERA AGENT → CONNEXION SORTANTE`

---

# 6. TEST CAMERA AGENT DISTANT

Vérifier :

### TEST 1

Agent démarre derrière NAT.

Résultat attendu :

`CONNECTED`

### TEST 2

Agent établit sa connexion sortante.

### TEST 3

Agent s'authentifie.

### TEST 4

Agent est associé à la caméra autorisée.

### TEST 5

Agent publie le flux.

### TEST 6

Media Gateway reçoit le flux.

### TEST 7

BurkinaWatch peut autoriser un viewer.

### TEST 8

Le viewer reçoit réellement la vidéo.

---

# 7. TEST CGNAT

Si le réseau est derrière CGNAT :

documenter :

* type de réseau ;
* IPv4 publique éventuelle ;
* IPv6 éventuelle ;
* comportement NAT ;
* connexion sortante ;
* possibilité ou impossibilité de connexion entrante ;
* comportement WebRTC ;
* nécessité de TURN.

NE PAS conclure qu'un réseau est "compatible CGNAT" simplement parce que l'agent peut joindre le backend.

Il faut également vérifier le chemin média.

---

# 8. TEST WEBRTC / STUN / TURN

Tester le flux dans au moins un navigateur desktop moderne.

Vérifier :

* ICE gathering ;
* ICE connection ;
* candidate type si disponible ;
* connexion directe si possible ;
* TURN relay si nécessaire ;
* temps de connexion ;
* stabilité.

Documenter clairement :

### DIRECT

ou

### STUN

ou

### TURN

Ne pas activer ou imposer TURN sans preuve technique.

Si TURN est nécessaire :

documenter pourquoi.

---

# 9. TEST DE BOUT EN BOUT

C'est le test principal de cette phase.

Réaliser réellement :

`CAMÉRA IP`
↓
`CAMERA AGENT`
↓
`MEDIA TRANSPORT VALIDÉ PHASE 8.2`
↓
`MEDIAMTX / VIDEO GATEWAY`
↓
`WEBRTC / WHEP`
↓
`BURKINAWATCH`
↓
`NAVIGATEUR`
↓
`IMAGE VIDÉO RÉELLE`

Le test doit confirmer que la vidéo est réellement visible.

Un :

`HTTP 200`

n'est PAS une preuve suffisante.

Un :

`stream exists`

n'est PAS une preuve suffisante.

Un :

`WebRTC session created`

n'est PAS une preuve suffisante.

Il faut confirmer que le navigateur reçoit effectivement les données média.

---

# 10. MESURES END-TO-END

Mesurer si possible :

* temps entre ouverture du viewer et première image ;
* stabilité ;
* latence approximative ;
* interruptions ;
* reconnexion ;
* consommation réseau ;
* CPU agent ;
* CPU Media Gateway ;
* nombre de viewers.

Les mesures n'ont pas besoin d'être extrêmement précises pour cette phase, mais elles doivent être réelles.

---

# 11. TEST COUPURE CAMÉRA

Procédure :

1. caméra online ;
2. viewer actif ;
3. couper caméra ;
4. observer état ;
5. remettre caméra ;
6. observer reconnexion.

Vérifier :

`LIVE → OFFLINE → RECONNECTING → LIVE`

ou le comportement réellement implémenté.

Documenter le résultat réel.

---

# 12. TEST COUPURE INTERNET DE L'AGENT

Procédure :

1. agent connecté ;
2. flux actif ;
3. couper temporairement la connexion réseau ;
4. observer ;
5. restaurer réseau ;
6. observer reconnexion.

Vérifier :

* backoff ;
* absence de boucle agressive ;
* heartbeat ;
* récupération du stream ;
* récupération du viewer.

---

# 13. TEST REDÉMARRAGE AGENT

Redémarrer le Camera Agent.

Vérifier :

* reconnexion ;
* authentification ;
* récupération de la caméra ;
* republication du flux ;
* récupération du viewer.

---

# 14. TEST MEDIA GATEWAY

Si possible en environnement de test contrôlé :

* arrêter Media Gateway ;
* observer ;
* relancer ;
* observer.

NE PAS redémarrer un composant de production sans autorisation explicite.

Si le test ne peut pas être réalisé sans risque :

marquer :

`NOT TESTED — PRODUCTION SAFETY`

et documenter comment il devra être testé en préproduction.

# 15. TEST AUTHENTIFICATION

Tester :

### UTILISATEUR NON CONNECTÉ

→ refus.

### UTILISATEUR CONNECTÉ MAIS NON PROPRIÉTAIRE

→ refus.

### PROPRIÉTAIRE

→ accès autorisé.

### AGENT RÉVOQUÉ

→ publication refusée.

### CAMÉRA SUPPRIMÉE

→ publication refusée.

---

# 16. TEST TOKEN VIEWER

Tester :

* token valide ;
* token expiré ;
* token falsifié ;
* token d'un autre utilisateur ;
* token d'une autre caméra ;
* token d'un stream différent ;
* session révoquée.

Tous les accès non autorisés doivent être refusés.

---

# 17. TEST IDOR

Tester explicitement :

Utilisateur A essaye d'accéder à :

* caméra B ;
* agent B ;
* stream B ;
* viewer session B ;
* token B ;
* status B.

Tout doit être refusé.

---

# 18. TEST SSRF

Vérifier que les protections SSRF existantes fonctionnent toujours.

Tester des variantes :

* localhost ;
* loopback ;
* IP privée ;
* link-local ;
* metadata ;
* IPv6 privée ;
* redirections ;
* formats IP alternatifs.

NE PAS désactiver SSRF pour faire fonctionner le test.

---

# 19. MULTI-CAMÉRAS

Si plusieurs caméras de test sont disponibles :

tester :

Camera A → LIVE

Camera B → LIVE

Camera C → OFFLINE

Vérifier l'indépendance des états.

Un flux défaillant ne doit pas casser les autres.

# 20. MULTI-VIEWERS

* consommation ;

* limite éventuelle de viewers.

# RÈGLE FINALE

La priorité absolue est la preuve réelle.

Ne pas dire :

"ça devrait fonctionner".

Ne pas dire :

"l'architecture permet".

Ne pas dire :

"MediaMTX est configuré".

Nous voulons savoir :

**EST-CE QUE LA VIDÉO RÉELLE PASSE DE LA CAMÉRA DISTANTE JUSQU'AU NAVIGATEUR D'UN UTILISATEUR AUTORISÉ ?**

Si oui :

documenter la preuve.

Si non :

identifier exactement où la chaîne casse.

À la fin, répondre :

**PHASE 9.1 — TERMINÉE**

puis :

**VERDICT : READY FOR PHASE 10**
ou
**VERDICT : READY WITH CONDITIONS**
ou
**VERDICT : NOT READY**
