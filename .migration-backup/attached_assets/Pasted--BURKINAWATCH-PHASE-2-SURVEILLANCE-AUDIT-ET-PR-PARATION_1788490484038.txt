# BURKINAWATCH — PHASE 2

## SURVEILLANCE — AUDIT ET PRÉPARATION DE L’ARCHITECTURE CAMÉRAS IP

Tu travailles sur le projet **BurkinaWatch**.

Le projet est une plateforme citoyenne existante.
La priorité absolue est de **préserver toutes les fonctionnalités existantes** et d'introduire progressivement une nouvelle fonctionnalité appelée :

# SURVEILLANCE

Cette fonctionnalité permettra à un utilisateur BurkinaWatch qui possède ou exploite une caméra IP chez lui, dans son commerce, son bureau, son atelier, son établissement, etc., de connecter cette caméra à son compte BurkinaWatch et de consulter son flux vidéo en direct depuis une interface sécurisée.

---

# ⚠️ RÈGLES ABSOLUES

Avant toute modification :

1. Inspecte réellement le dépôt et son architecture actuelle.
2. Ne suppose pas que certaines fonctionnalités existent.
3. Ne réécris pas le projet.
4. Ne refactorise pas massivement `server/routes.ts`.
5. Ne modifie pas les fonctionnalités existantes inutilement.
6. Ne supprime aucune table existante.
7. Ne supprime aucune donnée.
8. Ne fais jamais :

   * `db:push`
   * `db:push --force`
   * `drizzle-kit push`
   * reset de base
   * DROP TABLE
   * TRUNCATE
   * suppression/recréation de tables existantes
9. N'utilise aucune vraie caméra pour cette phase.
10. Ne demande jamais à l'utilisateur de rendre un port RTSP public sur Internet.
11. Ne stocke jamais les mots de passe caméra en clair.
12. Ne mets jamais de credentials caméra dans :

* le frontend
* les logs
* les URLs publiques
* le code source
* Git
* les variables exposées au navigateur.

13. Ne modifie pas la configuration Railway de production sans nécessité.
14. Ne commence PAS encore l'enregistrement vidéo.
15. Ne commence PAS encore l'IA vidéo.
16. Ne commence PAS encore les alertes intelligentes.
17. Ne commence PAS encore l'intégration d'une vraie caméra.

Cette phase est une phase **d'audit, d'architecture et de préparation**.

# 2. OBJECTIF DE CETTE PHASE

Nous voulons déterminer précisément comment intégrer :

```text
CAMÉRA IP
    ↓
RTSP / ONVIF
    ↓
PASSERELLE VIDÉO
    ↓
WEBRTC
    ↓
BURKINAWATCH
```

Architecture cible :

```text
                    BURKINAWATCH

Utilisateur
     │
     ▼
Frontend React / Mobile
     │
     │ HTTPS
     ▼
Backend Express
     │
     ├── Authentification
     ├── Autorisation
     ├── Gestion des caméras
     ├── Credentials chiffrés
     ├── Tokens temporaires
     └── Contrôle du flux
              │
              ▼
       VIDEO GATEWAY
       (ex. MediaMTX)
              │
              ▼
        RTSP / ONVIF
              │
              ▼
          CAMÉRA IP
```

IMPORTANT :

Le backend Express ne doit PAS devenir un serveur vidéo.

Il doit rester le **control plane**.

Le système vidéo doit constituer le **media plane**.

# 6. PROBLÈME CRITIQUE : CAMÉRAS DERRIÈRE NAT

Analyse le problème suivant :

Une caméra peut être située :

* chez un particulier
* dans une boutique
* dans un bureau
* derrière une box
* derrière un routeur 4G/5G
* derrière CGNAT
* avec une adresse IP privée.

L'utilisateur ne doit pas être obligé de :

* transférer un port RTSP
* exposer directement la caméra à Internet
* désactiver son firewall
* donner son IP publique au frontend.

Propose une architecture sécurisée permettant éventuellement :

```text
Caméra
   ↓
Agent / Gateway local
   ↓
Connexion sortante sécurisée
   ↓
Infrastructure BurkinaWatch
   ↓
WebRTC
   ↓
Utilisateur
```

Détermine si un **gateway local / agent** sera nécessaire pour le MVP.

Ne développe pas cet agent maintenant.

# 8. AUTORISATION

Conçois le modèle d'accès suivant :

Un utilisateur A :

* peut voir ses propres caméras
* peut modifier ses propres caméras
* peut supprimer ses propres caméras
* peut démarrer/arrêter l'accès à ses propres flux

Un utilisateur B :

* ne peut jamais lire les caméras de A
* ne peut jamais modifier les caméras de A
* ne peut jamais supprimer les caméras de A
* ne peut jamais obtenir le flux de A.

Les administrateurs doivent avoir uniquement les permissions nécessaires.

Vérifie comment intégrer cela aux helpers d'autorisation existants :

* `requireAuthenticatedUser`
* `requireResourceOwnership`
* `requirePermission`
* autres helpers réellement présents.

Ne crée pas un deuxième système d'autorisation parallèle sans raison.

# 9. SSRF

Le système caméra est particulièrement sensible au SSRF.

Analyse précisément la protection SSRF déjà présente.

Vérifie qu'une future caméra ne puisse pas être utilisée pour demander au serveur d'accéder à :

* localhost
* 127.0.0.1
* réseau privé
* metadata cloud
* réseau interne
* services Railway
* services Docker
* ports arbitraires.

Attention :

Une caméra IP utilise souvent une adresse privée légitime.

Il faut donc distinguer :

### Cas utilisateur → caméra personnelle

d'un :

### Cas attaquant → infrastructure interne.

Propose une stratégie réaliste pour cette distinction.

Ne désactive surtout pas la protection SSRF globalement.

* comment éviter les logs accidentels.

# 11. TOKENS VIDÉO TEMPORAIRES

Propose un mécanisme permettant :

```text
Utilisateur authentifié
        ↓
Demande accès caméra
        ↓
Backend vérifie ownership
        ↓
Backend délivre autorisation temporaire
        ↓
Gateway vidéo
        ↓
WebRTC
```

Le navigateur ne doit jamais recevoir :

* mot de passe caméra
* credential RTSP
* secret permanent
* token permanent.

Les tokens vidéo doivent être :

* courts
* liés à l'utilisateur
* liés à la caméra
* expirables
* révocables si possible.

Ne code pas encore ce système si l'architecture finale n'est pas suffisamment définie.

# 15. RISQUES À ÉVALUER

Fais une analyse spécifique des risques :

### Critiques

* accès caméra d'un autre utilisateur
* fuite de credentials
* exposition RTSP publique
* SSRF
* accès sans authentification
* token vidéo permanent
* compromission du gateway.

### Élevés

* brute force caméra
* reconnaissance réseau
* enumeration des camera IDs
* flux non chiffré
* logs contenant des secrets
* abus de bande passante
* DoS par flux vidéo.

### Moyens

* caméra offline
* reconnexion
* timeout
* UX
* quota.

# 16. TESTS À PRÉPARER

Propose une stratégie de tests avant implémentation.

Minimum :

### Auth

Utilisateur non connecté → refus.

### Ownership

Utilisateur A → caméra A → OK.

Utilisateur A → caméra B → REFUS.

Utilisateur B → caméra A → REFUS.

### Credentials

Vérifier qu'un GET API ne retourne jamais le mot de passe.

### SSRF

Tester les destinations interdites.

### Token

Token expiré → refus.

Token caméra A utilisé pour caméra B → refus.

### Logs

Aucun secret caméra dans les logs.

### Flux

Caméra offline → état `offline`.

### Reconnexion

Caméra revient → état `online`.
