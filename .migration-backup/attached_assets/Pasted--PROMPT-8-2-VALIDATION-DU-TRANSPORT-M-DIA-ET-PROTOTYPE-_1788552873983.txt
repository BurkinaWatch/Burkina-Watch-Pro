# PROMPT 8.2 — VALIDATION DU TRANSPORT MÉDIA ET PROTOTYPE CAMERA AGENT → MEDIAMTX

## CONTEXTE

BurkinaWatch dispose maintenant d’une architecture de surveillance vidéo séparant clairement :

* le **Control Plane** : BurkinaWatch / Express ;
* le **Media Plane** : MediaMTX / WebRTC ;
* les caméras IP ;
* le futur **Camera Agent** installé dans le réseau local de l’utilisateur.

Le Prompt 8 a défini l’architecture de production.

Le Prompt 8.1 a préparé l’architecture et le mécanisme de contrôle du Camera Agent.

Cependant, le Camera Agent actuel **ne transporte encore aucun flux vidéo**.

Les éléments suivants restent volontairement non implémentés :

* transport média réel Agent → MediaMTX ;
* caméra physique ;
* test LAN/WAN/CGNAT/4G/5G ;
* STUN/TURN ;
* MediaMTX distant ;
* stockage persistant sécurisé du credential caméra côté Agent ;
* fonctionnement multi-instance avec état partagé ;
* charge réelle multi-agents.

Le dernier audit a explicitement conclu qu’il ne fallait pas inventer un protocole média non validé.

---

# OBJECTIF DE CETTE PHASE

Cette phase doit répondre à une seule question principale :

> **Quel est le mécanisme technique correct, sécurisé et réellement supporté permettant au Camera Agent de prendre un flux vidéo local et de l’acheminer vers MediaMTX, sans exposer la caméra sur Internet ?**

Puis construire un **prototype fonctionnel de bout en bout en environnement local/dev uniquement**.

La chaîne cible de cette phase est :

```text
┌──────────────────────┐
│ Source vidéo de test │
│      RTSP            │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│    Camera Agent      │
│      local           │
└──────────┬───────────┘
           │
           │ transport média validé
           ▼
┌──────────────────────┐
│       MediaMTX       │
│     Media Plane      │
└──────────┬───────────┘
           │
           │ WHEP/WebRTC
           ▼
┌──────────────────────┐
│     BurkinaWatch     │
│      navigateur      │
└──────────────────────┘
```

## IMPORTANT

Cette phase ne constitue PAS une mise en production.

Elle ne doit PAS :

* exposer une caméra sur Internet ;
* ouvrir le port RTSP 554 publiquement ;
* utiliser une DMZ ;
* utiliser UPnP ;
* désactiver le firewall ;
* déployer un TURN public ;
* déployer le système chez des utilisateurs réels ;
* modifier l’architecture de sécurité existante pour faciliter le prototype.

# 2. NE PAS INVENTER LE PROTOCOLE MÉDIA

C’est la règle principale de cette phase.

Avant d’écrire le transport Agent → MediaMTX, déterminer précisément les mécanismes officiellement supportés par la version de MediaMTX utilisée par le projet.

Vérifier notamment les possibilités de :

* publication RTSP ;
* publication WebRTC ;
* publication SRT ;
* publication RTMP ;
* API ;
* authentification ;
* TLS ;
* transport TCP ;
* transport UDP ;
* mécanismes de push/publish ;
* mécanismes de pull/read ;
* configuration dynamique ;
* API de contrôle ;
* hooks éventuels.

Utiliser la documentation officielle de la version réellement utilisée.

Ne pas supposer qu’une fonctionnalité existe simplement parce qu’elle existe dans une autre version.

# 4. CRITÈRE DE CHOIX

Le protocole choisi doit respecter autant que possible :

1. connexion sortante depuis le réseau local ;
2. aucun port RTSP public ;
3. authentification ;
4. chiffrement lorsque nécessaire ;
5. compatibilité MediaMTX ;
6. reconnexion ;
7. séparation Control Plane / Media Plane ;
8. faible latence ;
9. simplicité opérationnelle ;
10. possibilité d’évolution vers NAT/CGNAT.

Ne pas choisir une technologie simplement parce qu’elle est facile à coder.

---

# 5. ATTENTION À L’ARCHITECTURE NAT/CGNAT

Ne pas confondre :

```text
Camera Agent → MediaMTX
```

avec :

```text
Navigateur → Camera Agent
```

L’objectif est précisément d’éviter la seconde architecture.

Le navigateur ne doit jamais avoir besoin de contacter directement l’Agent.

Architecture souhaitée :

```text
Camera Agent
      │
      │ OUTBOUND
      ▼
Media infrastructure
      │
      ▼
WebRTC
      │
      ▼
Browser
```

# 6. SOURCE VIDÉO DE TEST

Ne pas commencer par une caméra physique.

Utiliser une source vidéo de test contrôlée.

Par exemple :

```text
fichier vidéo local
        ↓
FFmpeg/GStreamer
        ↓
flux RTSP de test
        ↓
Camera Agent
```

ou toute autre source de test reproductible.

La source doit être clairement identifiée comme :

```text
TEST SOURCE
```

Elle ne doit pas être présentée comme une caméra utilisateur réelle.

---

# 7. CAMÉRA DE TEST

Si le repository dispose déjà d’une caméra virtuelle ou d’un flux RTSP de test, le réutiliser.

Sinon créer uniquement une source locale de test.

Ne pas :

* scanner le LAN ;
* découvrir automatiquement les caméras ;
* tester des adresses arbitraires ;
* tenter de trouver des caméras sur Internet.

---

# 8. PREMIER PROTOTYPE : SOURCE → AGENT

Faire fonctionner :

```text
TEST RTSP SOURCE
       ↓
CAMERA AGENT
```

L’Agent doit être capable de :

* se connecter au flux ;
* vérifier que le flux est valide ;
* détecter la perte du flux ;
* se reconnecter ;
* exposer uniquement l’état nécessaire au Control Plane.

Le Camera Agent ne doit pas devenir un proxy réseau générique.

---

# 9. TRANSPORT AGENT → MEDIAMTX

Une fois le protocole choisi :

implémenter uniquement le transport validé.

Exemple conceptuel :

```text
Camera Agent
     │
     │ publish
     ▼
MediaMTX
     │
     │ WHEP
     ▼
Browser
```

Le mécanisme exact doit correspondre à la décision documentée dans :

```text
docs/PHASE_8_2_MEDIA_TRANSPORT_DECISION.md
```

Ne pas implémenter plusieurs transports simultanément.

---

# 10. AUTHENTIFICATION DU PUBLISHER

Le Camera Agent ne doit pas publier anonymement.

MediaMTX doit pouvoir identifier le publisher.

Utiliser :

* credentials dédiés ;
* token ;
* mécanisme d’authentification supporté ;
* ou autre mécanisme sécurisé réellement compatible avec MediaMTX.

Ne jamais utiliser :

```text
SESSION_SECRET
MASTER_ENCRYPTION_KEY
REFRESH_TOKEN_SALT
DATABASE_URL
RAILWAY_DATABASE_URL
```

comme credential média.

---

# 11. IDENTITÉ DU FLUX

Chaque flux doit avoir une identité déterministe.

Conceptuellement :

```text
agentId
cameraId
streamId
```

Ne pas exposer :

* mot de passe RTSP ;
* URL RTSP complète ;
* credentials ;
* secret d’authentification média

au frontend.

---

Maintenir strictement :


### Media Plane

MediaMTX :


```text

```

```text

```

---

# 13. VIDEO GATEWAY

Réutiliser l’abstraction `VideoGateway` si elle existe déjà.

Elle doit rester indépendante du fournisseur média.

Conceptuellement :

```text
interface VideoGateway {
  registerStream(...)
  removeStream(...)
  getStreamStatus(...)
  createViewerAccess(...)
  revokeViewerAccess(...)
}
```

Adapter exactement à l’architecture réelle du projet.

Ne pas créer une deuxième abstraction concurrente.

---

# 14. STREAM REGISTRATION

Le Control Plane doit pouvoir associer :

```text
User
  ↓
Camera
  ↓
Agent
  ↓
Stream
```

Le Media Plane doit connaître le flux nécessaire.

Ne pas exposer au navigateur des paramètres internes inutiles.

---

# 15. URL DU FLUX

Le frontend ne doit jamais recevoir :

```text
rtsp://user:password@192.168.x.x:554/...
```

Le frontend doit recevoir uniquement ce qui est nécessaire pour établir la lecture WebRTC/WHEP.

Les URLs internes et credentials doivent rester côté serveur/MediaMTX.

---

# 16. TOKEN DE LECTURE

Le navigateur doit utiliser un mécanisme d’accès temporaire.

Le token doit idéalement être :

* court ;
* expirant ;
* lié à l’utilisateur ;
* lié à la caméra ;
* lié au stream ;
* révocable lorsque l’architecture le permet.

Un utilisateur ne doit pas pouvoir transformer son token :

```text
Camera A
```

en accès :

```text
Camera B
```

---

# 17. WEBRTC / WHEP

Réutiliser le lecteur WebRTC/WHEP déjà présent s’il existe.

Sinon créer le minimum nécessaire.

Le navigateur ne doit jamais tenter :

```text
RTSP
```

directement.

Le chemin attendu est :

```text
MediaMTX
   ↓
WHEP/WebRTC
   ↓
Browser
```

---

# 18. ÉTATS FRONTEND

Le lecteur doit distinguer au minimum :

```text
IDLE
CONNECTING
LIVE
OFFLINE
DEGRADED
ERROR
DISCONNECTED
```

Ne pas afficher :

```text
LIVE
```

simplement parce que le serveur a répondu HTTP 200.

Le frontend doit refléter réellement l’état du lecteur WebRTC.

---

# 19. RECONNEXION DU FLUX

Tester :

```text
Source vidéo
      ↓
Agent
      ↓
MediaMTX
      ↓
Browser
```

Vérifier :

```text
LIVE
↓
DISCONNECTED/OFFLINE
↓
source restaurée
↓
reconnexion
↓
LIVE
```

Tester également le redémarrage de MediaMTX.

---

# 20. RECONNEXION AGENT

Tester :

```text

↓
MediaMTX arrêté
↓
MediaMTX redémarré
↓
Agent reconnecte
↓
flux récupéré
```

L’Agent doit utiliser un backoff.

Ne pas générer des milliers de tentatives par seconde.

---

# 21. SÉCURITÉ DU FLUX

Vérifier que :

* aucune caméra n’est exposée publiquement ;
* aucun RTSP entrant public n’est nécessaire ;
* aucun port 554 Internet n’est ouvert ;
* MediaMTX admin n’est pas public ;
* les credentials ne sont pas dans les logs ;
* les tokens ne sont pas dans les logs ;
* les secrets ne sont pas dans Git ;
* le frontend ne reçoit aucun secret caméra.

---

* connexion ;
* publication ;
* déconnexion ;
* reconnexion ;
* erreur ;
* révocation.


---

# 23. SSRF

Ne pas supprimer ni contourner le validateur SSRF existant.

Si l’Agent reçoit une adresse de caméra :

* validation stricte ;
* contrôle du protocole ;
* contrôle des adresses privées selon l’architecture ;
* protection DNS rebinding ;
* validation avant connexion.

Documenter pourquoi certaines adresses locales peuvent être autorisées **uniquement dans le contexte du réseau local de l’Agent**.

Ne pas transformer cette exception en bypass SSRF global du serveur.

# 24. CREDENTIALS CAMÉRA

Cette phase doit déterminer comment les credentials caméra doivent circuler.

Architecture à privilégier :

```text
Control Plane
     │
     │ credential protégé
     ▼
Camera Agent
     │
     ▼
Camera
```

Mais ne pas encore considérer cette partie comme terminée si le stockage sécurisé local n’est pas correctement conçu.

Évaluer :

* stockage local chiffré ;
* permissions du fichier ;
* secret de déchiffrement ;
* rotation ;
* suppression ;
* mémoire ;
* logs ;
* crash dumps éventuels.

Si une solution sécurisée n’est pas encore disponible :

**ne pas stocker un mot de passe en clair simplement pour faire fonctionner la démo.**

Utiliser une source de test sans authentification ou des credentials temporaires de test clairement isolés.

---

# 25. NE PAS IMPLÉMENTER LE STOCKAGE FINAL À LA HÂTE

Le stockage persistant sécurisé des credentials côté Agent est une problématique distincte.

Si sa conception nécessite une décision d’architecture supplémentaire :

* documenter le problème ;
* proposer les solutions ;
* ne pas introduire une solution faible simplement pour obtenir `LIVE`.
